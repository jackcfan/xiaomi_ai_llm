# NAS 模型与 TTS 合并服务（hub）设计

日期：2026-11-22
状态：草案，待确认

## 1. 意图与背景

现状：小米 S12A 音箱上的 `device/native_first_client.sh` 在 `LLM_PIPELINE=native` 模式下**直连 DeepSeek 官方 API** 拿回答文本，再把文本发给 NAS 上 8080 端口的 TTS 服务（`server/`，`--mode tts-only`）合成播放。模型、提示词、历史都在设备端：提示词写在 `/data/native_first.env`，历史是 `/tmp` 里最近 6 轮、重启即丢；改配置要进 rdinit 改 env（SSH 不可用，每次都要断电）。

目标：把"调模型"和"TTS"合并成 NAS 上一个服务（以下称 **hub**），设备只调用 `http://192.168.100.100:9999`。模型供应商、提示词、性格、历史全部放在服务端，用 SQLite 保存，配一个简易网页后台管理；同时支持用语音切换模型和性格。这样以后改配置、换模型都不用再碰设备。

## 2. 目标

1. hub 是一个独立服务，监听 `0.0.0.0:9999`，对设备提供"文字进、流式 WAV 出"的接口，**格式与现有 `/api/v1/stream/text_chat` 兼容**（见 §6.1），设备客户端基本不改。
2. 所有可变数据存在**项目根目录**的一个 SQLite 文件（建议 `hub.db`）：模型供应商配置、性格（含提示词和音色）、当前模型、当前性格、全部对话历史。
3. 简易网页后台：管理模型供应商（增删改、选当前）、管理性格（增删改、选当前）、查看对话历史、查看/改上下文参数。
4. 多模型供应商：后台填接口地址 + key + 模型名即可新增；本期按 OpenAI 兼容接口实现（DeepSeek、Kimi、GLM、MiniMax 都是）。
5. 性格：预设列表，每个性格 = 名称 + 提示词 + EdgeTTS 音色。当前性格是**全局设置**，一直生效直到再改（语音和后台改的是同一个值），重启保持。
6. 语音命令（服务端规则识别，不依赖模型函数调用）：
   - 切换性格：如"换成毒舌模式""切换到温柔"——匹配后台已有的性格名。
   - 切换模型：如"切换到 Kimi""换成 DeepSeek"——匹配后台已有的供应商/模型名称或别名。
   - 清空上下文：如"忘掉刚才的对话"；"换个话题""重新开始"同样视为清空（我的决定：设备追问关闭时这些话会原样到达 hub）。
   - 命中后：改设置并用 TTS 回一句确认（如"好的，已切换为毒舌"），不调模型。未命中规则一律按普通问答。
7. 上下文：按**连续对话**判定——当前提问与上一条历史间隔 ≤ 5 分钟算同一段，整段带给模型；间隔 > 5 分钟开新段。另设轮数上限（默认 10 轮）。两个数值可在后台改。切换性格/模型**不清空**上下文；"忘掉刚才的对话"手动开新段。历史永久保存，"5 分钟"只决定发给模型的内容。播报中被唤醒打断（设备断开连接）时，hub 立即取消模型调用，保存已生成的部分回答并标记"被打断"，这部分照常进入后续上下文。（我的决定）
8. 联网搜索：把设备端现有的"规划 → DeepSeek 搜索/读取 → 带资料回答"流程移植到 hub，作为**独立模块**：无论当前回答用哪家模型，规划和搜索固定走 DeepSeek（`/v1/tools/search`、`/v1/tools/fetch`），因此 DeepSeek key 必须保持配置。搜索期间先播一句垫话（现为"搜索中，请稍等。"）。
9. 测试部署：先在开发 PC（当前 `192.168.100.99`）本地启动 hub，NAS 把 `9999` 端口转发到 PC；以后正式部署到 NAS 上时，设备地址不变。

## 3. 非目标（本期不做）

- 播放 NAS 音乐、在线搜索播放网络资源（下一阶段）。
- 用语音描述并新建性格（只从预设里选）。
- 后台登录/权限（仅家庭局域网使用）。
- 非 OpenAI 兼容的供应商（如 Claude 原生接口）。
- 改动设备固件、删除设备端直连 DeepSeek 的代码（保留作回退，`LLM_PIPELINE=native` 即可切回）。
- 下线 NAS 上现有 8080 TTS 容器（用户计划将来下线；设备不再依赖它）。

## 4. 反目标（即使"能跑"也算失败）

- 比现在更慢地开口：hub 模式下首声延迟明显高于当前 native 模式（当前日志首个 token 约 1.5–3 s）。
- 实时问题（如"世界首富是谁"）退化成模型旧知识，且不告诉用户。
- 设置在后台和语音两处不一致，或重启后丢失。
- 已经做好的设备端体验回退：问答全转 DeepSeek（`LLM_ROUTE_ALL_QA`）、拦截小爱开头（`aivs_speech_guard`）、播报中唤醒打断（`LLM_BARGE_IN`）在 hub 模式下失效。
- API key 出现在日志或后台页面的完整明文里。

## 5. 约束

- 设备是 BusyBox ash + curl + aplay，armhf 用户态；不能指望设备装新工具。设备 `/data` 改动只能经 rdinit（需要断电），所以**设备端只改一次配置**，之后所有变化都在 hub。
- 设备每次唤醒生成新的 `session_id`（如 `native_first_deepseek_<ts>_<pid>_<n>`），**不能用 session_id 判断连续对话**，必须按时间。
- 只有一台音箱、一个家庭，本期按单设备设计（不需要多租户）。
- 开发机是 Windows；hub 需能在 Windows 本地和 NAS（Docker，现有 `Dockerfile`/`docker-compose.yml`）上运行。
- 现有仓库 Python 依赖与 `server/` 代码可复用（`server/tts/edge_tts_client.py`、`server/sentence_splitter.py`、`server/streaming_pipeline.py` 的 WAV 流打包思路）。

## 6. 已定下的做法

### 6.1 方案选择（Approaches）

| 方案 | 做法 | 取舍 |
|---|---|---|
| A. 扩展现有 `server/main.py` | 在旧服务里加 SQLite、后台、性格、上下文 | 复用最多；但旧服务背着 ASR/whisper/shell 等历史功能和 `config.yaml`，两套配置来源会缠在一起 |
| **B. 同仓库新建独立服务 `hub/`（已选）** | FastAPI + SQLite，配置只认数据库；复用 EdgeTTS 与切句代码；通用 OpenAI 兼容客户端；接口格式兼容 `text_chat` | 结构干净，数据模型按需求设计，下一阶段（音乐）有地方放；联网搜索需从 shell 移植成 Python（A 也一样） |
| C. hub 只回文字，设备自己切句调 TTS | 设备流式逻辑全保留 | 设备两跳、延迟更高；性格音色要传回设备；违背"合并"初衷 |

用户选 B。

### 6.2 对设备的接口

- 保持与现有 `POST /api/v1/stream/text_chat` 相同：`multipart/form-data`，字段 `message`、`session_id`、`backend`、`speed`、`volume`；响应为**流式 WAV**（先发 RIFF 头，再持续写 PCM），设备 `http_stream_play` 用 curl 管道给 aplay 播放。hub 忽略 `backend`（以数据库当前模型为准）。
- 另提供 `GET /` 健康检查（设备 `init.sh` 启动时会探测 `SERVER`）。
- 提供 `POST /api/v1/tts/stream`（与现有接口同格式），用当前性格的音色，供设备播提示语等。（我的决定）
- **退回配置接口**（用户要求）：如 `GET /api/v1/device/fallback`，返回设备直连模式所需的配置：接口地址、API key、模型名、当前性格的提示词。需携带设备口令（如请求头 `X-Device-Token`），口令错误不返回 key。（口令为我的决定：避免局域网内任何人取走 key）后台可查看/修改退回配置与设备口令。退回配置可与"当前模型"不同（例如回答用 Kimi，退回固定 DeepSeek）。
- 设备一次性改配置（`/data/native_first.env`）：`SERVER=http://192.168.100.100:9999`、`LLM_PIPELINE=server`、新增设备口令；`TTS_SERVER` 也指向 hub（8080 将下线，用户决定）；原文件备份。
- 设备追问在当前 system1 方案下关闭，`/api/v1/route/asr`、`/api/v1/stream/chat` 本期不需要。（我的决定，实施前用设备上的实际 env 核对）

### 6.3 数据（SQLite，项目根目录）

至少包含：
- 供应商/模型：名称、别名（语音识别用）、接口地址、API key、模型名、温度/最大 token 等可选参数。
- 性格：名称、别名、提示词、EdgeTTS 音色名（如 `zh-CN-XiaoyiNeural`）。
- 设置：当前模型、当前性格、上下文间隔（默认 5 分钟）、上下文轮数上限（默认 10）、基础系统提示词（口语、不要 Markdown 等现有约束）。
- 对话历史：时间、用户问题、回答、所用模型、所用性格、是否联网及来源、是否语音命令、所属上下文段。

初始数据：首次启动时自动写入 DeepSeek 供应商（key 从环境变量或首次后台填写）和几个默认性格（默认/温柔/毒舌/撒娇），各配一个音色。

### 6.4 后台

- 服务端渲染的简单页面（不引入前端构建工具），与 hub 同端口，路径如 `/admin`。
- 页面：模型供应商、性格、历史（分页查看）、设置。
- API key 只显示后 4 位；日志中不打印 key。

## 7. 设备端还需要的改动（小）

现有 `LLM_PIPELINE=server` 路径（`send_text_and_play`，`native_first_client.sh` 中调用 `${SERVER}/api/v1/stream/text_chat` 处）需补齐今天在 native 路径上做的能力：
- **播报中唤醒打断**：在该路径调用 `http_stream_play` 前后写/删 `$LLM_PLAYING_MARKER`，被打断时走 `finish_llm_playback quiet`，不报错、不降级原生播报（与 native 路径一致）。
- 问答全转与开头拦截（`LLM_ROUTE_ALL_QA`、`aivs_speech_guard`）发生在路由阶段，与 pipeline 无关，预期不受影响，需实机确认。
- **连不上 hub 自动退回直连 DeepSeek**（用户选定）：
  - 客户端启动时请求一次退回配置接口，成功则把接口地址、key、模型名、性格提示词保存在**进程内存**（不写盘）；失败则用 env 里现有的直连配置。只在启动时拉取一次。
  - 每次问答前判断 hub 是否可用（如带短超时的健康检查），不可用则本次走现有 native 路径（直连模型 + 设备端历史）。此时 TTS 也不可用（`TTS_SERVER` 同在 hub），回答由小爱原生 TTS 整段朗读（现有 `TTS_FALLBACK_NATIVE=1` 行为），并亮**黄灯**提示处于退回模式（用户选定）。hub 恢复后无需重启客户端即回到 hub。
  - 现有 server 路径失败只会结束播放，设备拿不到回答文本，所以"连不上"必须在出声前判断出来，避免播了半截再退回造成重复。
- 转接提示音（PR #17 的 `LLM_ROUTE_BEEP`）：`route_beep_allowed` 要求 `TTS_ENGINE=device`，这台设备是 `TTS_ENGINE=server`，现在本来就不播，切到 hub 不算退化，本期不处理。（写计划时核对代码后更正）

## 8. 留给实现者决定

- `hub/` 内部模块划分、表结构细节、迁移方式。
- 语音命令规则的具体句式（需覆盖"切换到/换成/改成/用 X 模式/X 性格"等常见说法；需避免把"毒舌是什么意思"这类问题误判为切换）。
- 搜索规划的提示词与判定（可直接移植 `native_first_client.sh` 中 `BEGIN GENERATED NATIVE WEB` 段的逻辑与提示词）。
- 流式 WAV 采样率（现有 text_chat 为 32 kHz 16-bit 单声道，可沿用）。
- 启动方式（命令行入口、Docker 服务定义）。
- 测试方式（单测 + 用 curl 模拟设备请求 + 实机验收）。

## 9. 验收

- 设备改配置后：问答类经 hub 回答，首声延迟与当前 native 模式相当；控制/时间/天气仍由小爱处理。
- "世界首富是谁"类实时问题经联网回答，并简短说明来源和日期。
- 语音"换成毒舌模式"后，回答语气和音色都变化；后台显示同步；重启 hub 后仍保持。
- 语音"切换到 Kimi"（后台已配置 Kimi）后，历史记录显示所用模型为 Kimi。
- 连续追问 5 分钟内能接上文；停 5 分钟以上再问不带旧上下文；"忘掉刚才的对话"后不带上下文。
- 播报中唤醒可打断；小爱开头拦截仍有效。
- 后台改性格提示词/音色，下一次回答立即生效。
- 关掉 hub（PC 关机）后问答自动退回直连 DeepSeek，使用启动时拉取的退回配置，由小爱原声朗读并亮黄灯；hub 恢复后问答重新走 hub。
- 不带设备口令请求退回配置接口，拿不到 key。
